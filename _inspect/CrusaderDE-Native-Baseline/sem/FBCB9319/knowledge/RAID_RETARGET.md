# Raid target selection and attack access (FBCB9319)

Native DLL SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2`. The addresses below are RVAs for this binary only.

- `0x29190` appends a living building to its owner's bounded candidate list without checking raid-unit reachability or distance. `0x2C620` selects a building from that list using one of three 47-type priority tables. The Extender's `eStructs` enum identifies type `0x13` as `STRUCT_GRANARY` and `0x14` as `STRUCT_QUARRY`; both are intentional Vanilla candidates, regardless of whether this is desirable raid policy.
- `0x2C620` selects table RVA `0x2C7F80` when global `0x856A6D2 & 7` is 0-1, `0x2C7EC0` for 2-3, and `0x2C7E00` for 4-7. Their first priorities are respectively granary/armoury/churches, apple/cattle/wheat/hops farms followed by granary, and quarry/iron mine/pitch digger/wheat/hops/apple farm. All three tables also contain non-farm targets, including inns and barracks; wall tiles are not building entries in these lists.
- `0x2AE40` schedules the raid update `0x3E200`. For its ordinary harassment-group branch, `0x3E200` validates the stored target at tribe offsets `0x622` (building ID) and `0x626` (global ID), selects a replacement through `0x2C620` when needed, and calls `0x199C70` with command 9, building ID and global ID. The latter forwards to `0x11E960`.
- Command 9 in `0x11E960` writes building ID/global ID at manager-relative offsets `0x64C`/`0x650` plus `tribeId * 0x688`. The tribe array begins at manager offset `0x2A`, so these are the same stored-target fields at tribe-relative `0x622`/`0x626`; there is no second command-target pair at tribe-relative `0x64C`/`0x650`. The function filters eligible units, calls `0xDA020` to enumerate building attack positions, then `0x123090` to rank reachable candidates. Selected units receive movement through `0x196280`. The building can remain the stored raid target even when no suitable approach is assigned.
- `0xDA020` checks candidate positions around the building with height, occupancy and player-specific path-component conditions. It also has an alternate route check. A building's worker delivery access point is a separate contract and does not demonstrate a valid melee attack position.
- `0xDA020` writes 12-byte candidate records in the pathfinding context beginning at offset `0x1B344`; the first two 32-bit fields hold a position and its building-attack tile. `0x123090` filters/sorts this list, and command 9 tests the second field of the first record at offset `0x1B348` before issuing per-unit movement. The list is shared scratch state and must not be treated as a current command's result unless the command reached its candidate-generation path.
- List-end contract, checked against the installed machine code on 2026-10-01: `0x123090` iterates while the approach field is nonzero (`0x123228` and `0x1232B1`) and writes only a zero approach field at the filtered end (`0x1232C2`). The building field and score at that sentinel, and records beyond it, may retain old values. `0xDA020` normally clears both approach and building fields at its generated end (`0xDA56B`/`0xDA577`), but the filtered list must use the approach-only sentinel. A reader requiring both fields to be zero can consume stale tail records. The runtime bounds the read to 500 records; a missing sentinel within that limit remains uncertain.
- The command-9 consumer calls the builder at `0x11FF9A`, the filter at `0x11FFA7`, and checks the first building field at `0x11FFAC`; zero branches past the complete per-unit movement pass. Later paired records cannot rescue a failed first building-field gate. An empty list or a zero first building field therefore means no usable melee point only when the result is associated with the current command. Identical pre/post contents alone do not prove whether the search ran again or was bypassed; even two freshly generated empty lists can be identical. Ignored sentinel/tail fields must not manufacture a content-change freshness signal.
- `0x2C620` scans up to 100 16-bit building IDs in the victim player's resource record at offsets `0x3560..0x3627`; the 32-bit count is at `0x3628`. It compares each building type with the 47 entries in the priority table selected by global `0x856A6D2 & 7`. An equal-ranked later list entry replaces the earlier selection. `0x3E200` writes the selected building ID/global ID and a 100-tick raid pause after issuing command 9, so a post-command correction of its stored target must run after that outer call has returned.
- For the observed harassment group 0 (storage role 180), `0x3E200` reaches `0x2C620` when it needs a new building target. Neither `0x29190` nor this selection branch compares candidate coordinates with the group or previous target; same-rank ties follow candidate-list order, not proximity. Vanilla also has a distance-scoring selector at `0x2C710`, called by `0x30E90`, but the observed group-0 branch in `0x3E200` does not call it. This establishes behavior for this native path, not a claim about every game AI target selector.
- The `0x3560` and `0x3628` offsets above use the native record origin `module+0x379AE2C+playerId*0x583C`. `GamePlayerManagerAPI.TryGetPlayerResourcesById(playerId)` returns a pointer 0x5C bytes before that origin, so the same list/count are at API-pointer offsets `0x35BC` and `0x3684`. In the 2026-09-30 runtime log, module base `0x7FFEDE870000`, the Extender's player-1 resource pointer `0x7FFEE201060C`, and native player-1 list address `0x7FFEE2013BC8` independently establish that 0x5C displacement. Reading the unadjusted offsets yielded a false count of zero after Vanilla selected live granary `119/6450`.
- `0x2DC30` gates raid updates using tribe counters at offsets `0x5EA`, `0x5EC` and `0x5F0`; their exact gameplay meanings are not established here. Other writers of the stored target include `0x30620` and `0x30E90`, so a stored target change alone does not prove command 9 ran.
- The installed `0x3E200` loop ends at six entries (`0x3E61E`) and reads storage roles 180 through 185 from table RVA `0x2CF0D8`. The Extender labels these `HarassmentCombat0..5`; role 186 is `SiegeCover0`, not an extra raid group. The storage role resolves the current tribe ID and global ID for each player, so tribe ID alone is not a stable raid-group identity. Roles 1 and 2 also enter an alternate branch at `0x3E50B`: it tries `0x2D370`, then falls back to `0x2C620`. The ordinary building-attack branch for the other roles calls `0x2C620` at `0x3E46B`. The mod's replacement logic must therefore react to the observed command-9 event, not infer one from a role or stored-target change.
- In that regular role-1/2 branch, `0x2DC30` and the player's update counter gate action. `0x2D370` scans the victim's building-candidate list from a rotating start, accepting only the first eight types in table RVA `0x2C7E00`: quarry, iron mine, pitch digger, wheat/hops/apple/cattle farm, woodcutter's hut. If it returns no building, `0x2C620` supplies a candidate from the ordinary priority selector. Code at `0x3E55F..0x3E5DD` converts the chosen building to a tile, tests path-component connectivity via `0x3E650`/`0xE2610`, and issues a tribe move order through `0x11DD10` if connected. Otherwise it calls `0x3E9A0`, which may issue a move order to stored player fallback coordinates. This branch does not call the target-based command-9 building attack and does not test melee attack positions. The separate state-2 branch at `0x3E309..0x3E35D` precedes the role split and can affect any of the six roles; depending on its predicate it tries `0x2D370` or `0x2C8B0` before the same movement path. `0x2C8B0` uses the fixed `0x2C7E00` table across the candidate list. These are code-path findings, not observed orders for roles 1/2 in `Log_197.log`.
- The command-9 unit pass in `0x11E960` uses the type dispatch table at RVA `0x121FB0` with indices at `0x121FD0`. Melee-type cases (including ordinary European/Arab/Bedouin melee units, tunneler and Lord) increase the count used before the `0xDA020` approach search at `0x11FF9A`. Archer, crossbowman, Arab bow, slinger and Bedouin ambusher use a separate case that does not increase that count. Catapult, trebuchet, mangonel, ballista and Arab ballista use another case that can still receive command 9 without increasing the melee count; battering ram has a separate case. A missing melee pair is therefore insufficient to reject a target for a group containing building-capable siege units. Other special unit cases require individual validation before inclusion in the fix.
