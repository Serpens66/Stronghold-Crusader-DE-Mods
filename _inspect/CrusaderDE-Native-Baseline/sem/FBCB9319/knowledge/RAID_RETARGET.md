# Raid target selection and attack access (FBCB9319)

Native DLL SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2`. The addresses below are RVAs for this binary only.

- `0x29190` adds a living building to its owner's bounded candidate list without checking raid-unit reachability. `0x2C620` selects a building from that list using one of three 47-type priority tables. Type `0x14` is `STRUCT_GRANARY` and appears in all three tables, first in the table at VA `0x1802C7E00`. Granaries are therefore intentional Vanilla candidates, regardless of whether this is desirable raid policy.
- `0x2AE40` schedules the raid update `0x3E200`. For its ordinary harassment-group branch, `0x3E200` validates the stored target at tribe offsets `0x622` (building ID) and `0x626` (global ID), selects a replacement through `0x2C620` when needed, and calls `0x199C70` with command 9, building ID and global ID. The latter forwards to `0x11E960`.
- Command 9 in `0x11E960` writes building ID/global ID at manager-relative offsets `0x64C`/`0x650` plus `tribeId * 0x688`. The tribe array begins at manager offset `0x2A`, so these are the same stored-target fields at tribe-relative `0x622`/`0x626`; there is no second command-target pair at tribe-relative `0x64C`/`0x650`. The function filters eligible units, calls `0xDA020` to enumerate building attack positions, then `0x123090` to rank reachable candidates. Selected units receive movement through `0x196280`. The building can remain the stored raid target even when no suitable approach is assigned.
- `0xDA020` checks candidate positions around the building with height, occupancy and player-specific path-component conditions. It also has an alternate route check. A building's worker delivery access point is a separate contract and does not demonstrate a valid melee attack position.
- `0xDA020` writes 12-byte candidate records in the pathfinding context beginning at offset `0x1B344`; the first two 32-bit fields hold a position and its building-attack tile. `0x123090` filters/sorts this list, and command 9 tests the second field of the first record at offset `0x1B348` before issuing per-unit movement. The list is shared scratch state and must not be treated as a current command's result unless the command reached its candidate-generation path.
- `0x2C620` scans up to 100 16-bit building IDs in the victim player's resource record at offsets `0x3560..0x3627`; the 32-bit count is at `0x3628`. It compares each building type with the 47 entries in the priority table selected by global `0x856A6D2 & 7`. An equal-ranked later list entry replaces the earlier selection. `0x3E200` writes the selected building ID/global ID and a 100-tick raid pause after issuing command 9, so a post-command correction of its stored target must run after that outer call has returned.
- `0x2DC30` gates raid updates using tribe counters at offsets `0x5EA`, `0x5EC` and `0x5F0`; their exact gameplay meanings are not established here. Other writers of the stored target include `0x30620` and `0x30E90`, so a stored target change alone does not prove command 9 ran.

Runtime observation from `test_Raid_Retarget_Delay.sav`: player 2 harassment group 0 destroyed apple farm building `155/6649` at tick 704. Its stored target became granary `119/6450` by pre-tick 830; it retained that live target through tick 4209 without logged damage to it. The previous diagnostic lacked group-command and unit-path events, so the reason for the absent attack remains unconfirmed.

The later diagnostic session confirmed command 9 for granary `119/6450` after pre-tick 828. Through tick 2773 there was no damage to it and no per-unit destination adjacent to its footprint. The granary's `4x4` footprint begins at `407/515`; its `20` valid bounding-ring tiles include only three walkable, connected diagonal corners. The user also issued a manual building-attack order against that granary and observed no movement. These observations support an attack-access failure but do not yet prove whether `0xDA020` produced no candidates. A previous diagnostic field labelled `nativeCommandTarget=0/0` used the wrong pointer-relative offsets and is not evidence of a failed native command.
