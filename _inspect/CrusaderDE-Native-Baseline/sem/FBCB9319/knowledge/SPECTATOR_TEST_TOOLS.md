# Offline AI test tools: native request and resource contracts [Scope: Vanilla + mod integration]

Native SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2`.
Managed SHA-256: `BC8B6A395F01D48557DB413600C8DD8D1FDFD3ABDF97BFBBB68A3C56B04FD789`.
Extender 2.14.1 source commit `5908e1f12437deb7ef5f5b1dc2d64e301178fba3`,
tree `c238441ea12db35ee36c5c5668d3c8fce0897295`.

This is static feature evidence, not an in-game acceptance record. Autogenerated
function names remain candidate-level; the stated branches are supported by the
hash-matched function bodies and installed Extender source/assembly contracts.

`HUD_AlliesPanel.ButtonClicked` passes selected ally, selected goods and amount to
GameAction; UpdateGoods requires positive amounts and the sender's own inventory.
The private ally/enemy lists have six slots. A separate test view is needed to
avoid changing normal diplomacy and BugfixesAndQoL's spectator authorization.

`DLL_GameAction` (0x81870) dispatches the ally-order action to 0xD7520, which stages
Chore 113. At 0x1A6F0 the handler serializes a signed short request kind and four
signed 32-bit values. Kind zero invokes 0xD7580. That complete function is 587
bytes and takes `(attackTarget, orderedAi, requester, order)`, all player IDs
one-based. Order 10 clears the request; 11 requests protection of requester;
other attack values use attackTarget. This function does not check alliance
membership. It distinguishes AI/human slots, invokes the appropriate acceptance
check and writes request state only on acceptance for AI slots.

Defend acceptance 0x2A500 and attack acceptance 0x41500 require an initialized AI,
check help state and compare army strength to the AIC threshold. The installed
Extender owns both hooks and exposes OnPlayerAIEvaluateDefendOrder and
OnPlayerAIEvaluateAttackOrder. In these events TargetPlayerId is the ordered AI;
SourcePlayerId is requester; attack ContextPlayerId is the attack target.
Pre with SkipOriginalFunction and ReturnValue=true returns acceptance without
the original readiness check. The outer 0xD7580 then performs the normal writes
and accepted-attack preparation through 0x2A580 (which calls 0xC4080, 0x2B5F0,
0x304B0, 0x30550, then clears siege state). A context limited to one call can
therefore force acceptance without another native hook or direct order-field writes.

The request mode, attack target and requester map to Extender fields
r_AIAllyOrderMode (+0x384C), r_AIRequestedAttackTargetPlayerId (+0x3850), and
r_AIAllyOrderRequesterPlayerId (+0x38E4). Record stride is 0x583C. At 0x2F670
the target selector clears requests whose requester Lord is invalid; a valid
attack request retains the explicit target while that Lord remains valid.
0x3C2E0 handles protection through 0x3D020. Accepted request state alone does
not prove that troops can move or reach an objective.

Vanilla send-goods execution 0xD7AD0 adds physical recipient goods, removes
sender goods, updates valuation statistics and clears matching requests. Gold
is handled separately and capped by sender funds. The standard send action is
therefore unsuitable for creation from nothing. Existing Extender AddIncomingGood
adds to the delivery-reserve table (+0x46C base); AddPlayerGold changes signed
r_TotalGoodsGold (+0x50C). Both require caller-side overflow checks. Combining
stored goods and pending incoming goods before a new credit protects eventual
storage totals. Existing storage consumers 0xAED70 / 0xAF210 consume incoming
resources as capacity permits, update local/global goods and resource visuals;
editor mode excludes those simulation paths. Gold can be credited immediately.

EngineInterface's shared monitor is a private static System.Object field named
threadLock in the real assembly. An actual-assembly metadata check and a
single encapsulated reflection read are required; publicized direct access is invalid.

Executable fixture checks live under Testmods/SpectatorEditorBuildTest/tests;
the mod's UpdateToNewDLL.md records its supported origins, resolution limits,
existing placement hooks and outstanding in-game acceptance matrix.


## Defend eligibility, 2026-11-10 [Vanilla facts]

On the same native image, the Defend evaluator at RVA 0x2A500 accepts an
initialized AI when its help-block flag is zero and its signed eligible-army
count is at least the signed AIC rescue threshold. These are distinct from
the overall troop count and the accepted order fields. In the installed
Extender 2.14.3 (SHA-256 5CB1C33BE5463086505A17F5C48AAA357D733CFFF7240E101C821F0E3C668498)
the fields are GamePlayerResources.r_AILordMinusOne, N000040FB and N00004015;
the threshold is InternalAIC.siege_troops_before_will_come_to_rescue.

The help-block flag is written by RVA 0x2DFC0, which compares the nearby
hostile strength plus its piecewise margin against the AI's own near-keep
strength. RVA 0x182B00 counts units in the eligible AI roles. An allied AI
can therefore have an army in the HUD and still decline a Defend request.
A new order requires separate readback of the native order mode and
requester after acceptance.

## Power confirmation input, 2026-11-13 [Vanilla facts]

This input audit applies to native SHA-256
`FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2`
and managed SHA-256
`BC8B6A395F01D48557DB413600C8DD8D1FDFD3ABDF97BFBBB68A3C56B04FD789`.
The installed native hash was rechecked on 2026-11-13. The following parameter
flow and branches are confirmed by the hash-matched exports and managed bodies;
autogenerated function names themselves are not additional semantic evidence.

`EditorDirector.preDLLCallActions(ref int mouseOverX, ref int mouseOverY)` obtains
left-button state plus separate `rightDown` and `rightUp` values from private
`getMouseStateForEngine(ref bool rightDown, ref bool rightUp)`. It passes these
values through public `EngineInterface.TroopSelection` to `DLL_TroopSelection`.
The real `Assembly-CSharp.dll` declares `preDLLCallActions` public and instance,
`getMouseStateForEngine` private and instance, and the
`ConfigSettings.Settings_SH1RTSControls` getter public and static, returning bool.
A publicized compile reference does not authorize direct calls to the private method.

The canonical native export table identifies `DLL_TroopSelection` at RVA
`0x879A0` and `DLL_RunTick` at RVA `0x86680`. The former writes mouseState,
rightDown and rightUp to VA `0x1808EBA98`, `0x1808EBA93` and `0x1808EBA9C`
respectively. Managed `EngineInterface.run` calls `preDLLCallActions` before
`DLL_RunTick`, passing its resulting map tile and the current
`ConfigSettings.Settings_SH1RTSControls`. `DLL_RunTick` forwards the stored
button values to RVA `0x8C5F0` in this order:
`(leftState, rightDown, shiftPressed, SH1RtsControls, rightUp, ctrlPressed, altPressed)`.

At `0x8C5F0`, targeting mode 4 accepts a power target on the command-button DOWN
edge: when SH1RtsControls is false it requires rightDown != 0; when true it
requires leftState == 1. Sending only a left-state sequence 1 then 3 cannot
confirm a power under the false setting. With the true setting, a rightDown
instead enters the earlier cancellation branch through RVA `0x897F0`.
Mode 5 has a separate transition: under the true setting leftState 1 or 2
retains that mode; otherwise it returns to mode 4 before a later input pass.
The mode-4 input branch is still subject to its existing actor/state and target
eligibility checks. Spawn-power IDs 2, 3, 4 and 6 have additional spatial tests;
ArrowVolley ID 0 does not set the spawn-only eligibility flag in that branch.
On acceptance it stages selected power, target tile and local actor at VA
`0x1886C132C`, `0x1886C1330` and `0x1886C1334`, calls the chore enqueue routine
at RVA `0x23990` for opcode 119, and resets targeting mode to 0. These facts
establish input and staging, not eventual gameplay execution or performance.
