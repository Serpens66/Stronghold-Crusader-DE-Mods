# Multiplayer building sleep and local selection

Native build SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2`. The installed DLL hash was checked before using these RVAs. The functions below are identified by direct data flow; `DLL_GameAction` is a confirmed export, while the other symbolic roles are static reconstructions from candidate-labeled decompiler functions and references.

`MainViewModel.ButtonToggleZZZMode` calls `GameAction(ToggleSleep=1003, lastGameState.in_structure, 0)`. Native `DLL_GameAction` (`0x81870`, case `0x3EB`) stores the 1-based building ID in global `0x67E8394` and calls `0xD6F00`. That producer reads the selected record's building type, subject to a game-mode-specific early branch, then queues Chore 43. The Chore callback is table entry `0x2C7B88` (`0x2C7A30 + 43*8`) pointing to `0x13C10`. Its mode-1 path serializes **two bytes of building type** via `0x1F5F0`; its mode-0 path reads those two bytes and calls `0xD5980` with the Chore sender's player ID and the decoded type. It does not transmit a building ID.

`0xD5980` toggles the sender's per-type sleep flag and calls `0xC7E90`. For every alive building whose owner and type match the two arguments, `0xC7E90` updates the sleep state, clears local goods at record offsets `0x120` onward, and clears dependent references. The alternative branches are no matching record and an out-of-range type (`>=91`), which do not perform the reset. The periodic synchronizer at `0xC7D50` compares the building's sleep state with the per-type flag and resets on disagreement; the direct `0xC7E90` path already writes the new state. Native checksum builder `0x22020` hashes each building's `0xD0..0x32B` record interval, including iron at `0x138`, stone at `0x130`, and wood logs at `0x124`.

Fixes 1.19.1's installed `fixes.dll` patches the reset block at `0xC7F3E`. It reads Script Extender's `CurrentlySelectedBuildingIdVA`, which resolves to the same native global at `0x67E8394`, indexes the building array by ID minus one, and selects a preservation branch from that local building's type. On a receiving peer, Chore 43 supplies the sender's building **type** but never updates this local selected-building global. With a sender-selected iron mine containing iron and a receiver with no selected building, Fixes preserves iron only on the sender. The receiver takes the full-clear branch. The selected ID can also refer to an unrelated alive building, selecting the wrong preservation branch. The resulting resource field difference lies in the checksum interval.

This is a static counterexample for a reachable multiplayer command, not a captured runtime reproduction. The prior curated Chore-43 entry described a four-byte building ID payload from historical discussion; the current native producer and callback establish a two-byte building type instead.
