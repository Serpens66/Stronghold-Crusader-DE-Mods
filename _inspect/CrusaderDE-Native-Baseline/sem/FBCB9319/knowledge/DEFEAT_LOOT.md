# Lord defeat loot audit

Native SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2` (installed DLL verified). The owning unit-state function is `FUN_18015a950`, RVA `0x15A950`, VA `0x18015A950`; its autogenerated function name is a candidate, while the reward instructions and branch bytes below were independently checked against the installed binary.

The state-machine path reaches the one-shot lord-death branch after an already marked death (`unit manager + unitId*0x490 + 0xA69 == 99`) has been excluded. The defeated player's one-based ID comes from the unit owner word loaded at RVA `0x15C44F` into R8. The credited winner's one-based ID comes from the unit kill-attribution word loaded at `0x15C458` into EBP. The player-record stride is `0x583C`, matching the installed Script Extender's `GamePlayerResources` view. `0x15C475` tests the winner ID. Its `JE` at `0x15C477` skips to `0x15CDC3` if no winner exists; the following `CMP` at `0x15C47D` and `JNE` at `0x15C487` skip the reward for the special unit flag. The surrounding death-state branches, including the separate `0x6E` path and non-lord processing, do not enter the reward block.

At `0x15C48D` the reward block starts. Gold is signed `r_TotalGoodsGold` (`GamePlayerResources + 0x50C`); Vanilla awards truncated 25% of the defeated player's gold, clamped to 500..100000, directly to the credited winner. Twenty goods totals are read from the defeated player's `r_TotalGoods*` table and truncated 25% is added to the winner's `r_incoming*` table (`+0x46C` base). The goods-notification flag is set only if a positive goods amount was credited. The reward branch then records award statistics, clears the defeated player's goods and rejoins death-state, animation and notification handling. The no-winner and special-flag paths rejoin the same downstream state handler at `0x15CDC3` without those awards. There is no separate managed reward dispatch in this path; the native simulation writes the gold and pending goods directly.

The first testmod hook at `0x15C477..0x15C487` jumped human winners to `0x15CDC3`. The in-game test confirmed that this suppresses gold but also skips loser-goods cleanup, the type-8 kill notification, the type-1 gold notification and the `FUN_18003F640` follow-up. That target is therefore unsuitable when the kill notification must remain.

The first in-game test on 2026-09-26 exposed a RedBird context-stub flag hazard: both human Rat defeats incremented the callback's suppression count, but the game still credited and announced 500 gold. The installed `RedBird.X64.dll` (assembly version `1.5.0.0`) runs `sub rsp,144` before `pushfq` captures `Rflags`, then runs `add rsp,144` after `popfq` restores them. Thus the context does not expose the earlier Vanilla flags, and a changed `Rflags` does not survive to a relocated conditional branch. A post-callback `TEST` is required. The second in-game test verified suppression of gold but no kill notification, exposing the overly broad skip described above.

The narrower entry at `0x15C4EA` follows the winner guards and the `INC BYTE [R10+RBP+0x27AD01]` victory counter at `0x15C4DB`. `RBX` and `R14` already contain the defeated one-based player ID, `R11=R14*0x160F`, and `R12D` contains the clamped gold award (minimum 500). Its exact RedBird span is two seven-byte instructions, `IMUL R10,RBP,0x160F` and `IMUL R13,RBP,0x583C`, ending at `0x15C4F8`; the first gold write is at `0x15C4FC`. No direct incoming edge into the span interior was found in the Ghidra reference export. For a human winner, set `RCX=moduleBase+0x366C210`, `R12D=0`, `RDX=0` and branch to `0x15C980`. For AI/error, set `RDX=1` and execute both displaced instructions. RDX is dead on the AI path until overwritten by `IMUL ECX` at `0x15C512`, and the human path overwrites it with `XOR EDX,EDX` at `0x15C980`. The cleanup uses RCX, R11, RBX and zero R12D, then sets R13 itself at `0x15C988`; later R12 is overwritten at `0x15CA7B` or `0x15CAB1`.

The cleanup zeroes the defeated player's twenty goods totals at `0x15C98F..0x15C9FD`, updates the winner award statistic by `R12D` at `0x15C997`, applies mode-specific message guards at `0x15C99F..0x15CA25`, and queues the type-8 kill message via `FUN_18001C8D0` (RVA `0x1C8D0`, VA `0x18001C8D0`) at `0x15CA3B`. The type-1 gold message is prepared at `0x15CA40..0x15CA6A` and queued by the same function at `0x15CA6F`. A second hook at `0x15CA65` spans `MOV EDX,ESI; SUB R12D,EAX; MOV [RSP+0x20],R12D; CALL 0x1C8D0`, exactly 15 bytes, and skips to `0x15CA74` only when `R12D=0`. The branch leaves the earlier kill message and subsequent `FUN_18003F640` call at `0x15CA9B` intact. An AI award is never zero in this Vanilla branch, so all original instructions run for AI. The exact copied-buffer RedBird spans, generated stubs, and both transaction handles must be checked before publication.

The final in-game test confirmed that the two-hook design suppresses the human Rat victory reward while keeping the type-8 victory notification and omitting the type-1 gold notification. AI rewards and multiplayer parity still require separate in-game checks. ExtraFeatures 1.0.102 uses this design with independent human/AI settings; selecting either role routes that winner through the same audited zero-reward cleanup path.

The installed RedBird 1.5.0.0 `X64InlineHook` generated an RIP-relative indirect `JMP [RIP]` for each stub continuation. Iced reports `NearBranchTarget=0` for that instruction; validation must resolve its immediately following eight-byte pointer slot and compare the actual target. The two copied-buffer probes and generated-stub checks passed before the 2026-09-26 build/install. This is an assembler contract observation, not an in-game behavior confirmation.
