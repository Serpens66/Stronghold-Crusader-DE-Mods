plan or gameplay acceptance. The requested behavior is three independent options
for existing diggers, civilians and remaining military units. Together they should
cover player-associated units, including civilian work journeys, transports,
mounted units and movable siege equipment. Neutral wildlife is outside that request.
Existing immobile objects do not acquire a movement action merely by allowing a

## Coordinate, record and dispatch contracts

- Unit and building game IDs are one-based. Unit-manager addressing uses
  `manager + unitId * 0x490 + field`. The typed `GameUnit` view starts at manager
  record offset `0x65C`; some native bulk copy/save operations start at `0x658`.
  Those origins differ by four bytes and must not be interchanged.
- Current tile X/Y are signed 16-bit words at manager-relative `0x71C/0x71E`;
  native tile ID is the signed 32-bit field `0x72C`. Packed tile IDs use the
  native row lookup, not an unqualified `y * 800 + x`. Coordinate availability
  uses the separate 800-by-800 byte grid at RVA `0x3A11EA4`.
- `r_ControllableForPlayerId` is **UInt16** at typed offset `0x92`, manager-relative
  `0x6EE`. Native callers generally sign-extend this word for a player parameter.
  Valid normal players are 1..8. A decorative name, selectable state, tribe owner,
  currently selected player or current type-update global does not replace the
  actual moving unit's control-player field.
- Unit update dispatch at `0x18410C` uses the pointer table at `0x321CB0`
  (PE file offset `0x3202B0`). The current `eChimps` inventory has **89** real slots,
  0..88, and sentinel `CHIMP_NUM_TYPES = 89`. This is unrelated to the native
  90-entry stride of a different pathfinding connection table.
- All 89 dispatch entries are retained in the evidence JSON, including aliases,
  null/debug types, animals, transitional burning types and stationary objects.
  A handler address establishes dispatch ownership; its applicable movement and
  target branches are examined separately below.

## Ordinary requested movement, publication and consumption

### Requested path and its state

`0x196280` receives the unit manager, one-based unit ID, target tile coordinates
and a build/reconstruction selector. It reads the live type profile at
`0x322540 + unitType * 4`. Its movement start is the current tile only when path
state `+0x74E == 0` and substep `+0x750 == 8`; otherwise it is the next tile
`+0x738/+0x73A`. This start differs from the stored route-start fields during a step.

The completed-moat probe `0x196840` reads the bit-30 tile flag at the unit's
**current** tile. It has no unit-type, player or alliance test. A positive probe
sets path-manager/global moat mode `0x60AD6E4`; that value is not itself an
owner-safe permission. The separate probe `0x18E1E0` has scratch output and is not
the actual unit-route publisher.

Target bounds and availability, target flags, Large-profile surface restrictions,
PCL reachability and exit/intermediate-target paths precede the builder. A same
start/target returns success after stopping and clearing cursor/length. For an
actual build, the unit's 1000-byte path slot is cleared and bound to the path
manager, then `0xF4930` or `0xE32B0` runs. Successful publication writes positive
length `+0x754`, path state 2 at `+0x74E`, cursor 0 at `+0x752`, destination/start
fields, and the effective moat mode as a word at `+0x9C8` (typed `+0x36C`).
The global moat/Assassin mode qword is then cleared. The marker belongs to the
published unit path, not to an entire type or the last processed group member.

Argument identity matters: the second Windows-x64 argument of `F4930` is loaded
from the unit's `+0x6EE` **player ID**, and its third is the live 32-bit type
profile. Some mod parameter names call the former `movementClass`; that name
does not change its native origin. Conversely, `DCE60` argument 6 comes from
`+0x6EC`, the separate movement/control mode. These inputs are not interchangeable.

Failure does not constitute a full stop or a successful new path. `0x199CD0`
contains structure-exit/state handling, **not** a path-buffer memset. The buffer
clear already happened before the builder in `0x196280`; a failed search can
therefore leave zeroed or partially rewritten bytes with old path state, cursor
or length. Early target rejection can happen before that clear. This refines the
older failure description in [FIRE_EFFECTS.md](FIRE_EFFECTS.md); see the dated
correction there.
The outer invalid-target exit clears only the upper half of the global special-
mode pair in the inspected body. Do not assume every early exit clears both
global modes, or that a failed build writes a new valid per-unit marker.

### Builder and reconstruction choices

The complete ground/moat builder contract is also preserved in
[GROUND_ROUTE_BUILDERS.md](GROUND_ROUTE_BUILDERS.md). In brief:

- Ground mode chooses `0xF32B0` for Large (profile 0), `0xF3060` otherwise, then
  `0xDAAC0/0xDA590`, reconstruction `0xE1640` and, when required, `0xDB650`.
- Moat mode skips the ordinary region gate and straight attempt, tries
  `0xDAAC0`, then `0xDAFD0`; both failures return zero. Reconstruction is mode 2.
- The native moat graph has height, special-structure, corner and flag rules.
  It does not receive a player parameter. Search-mode selection alone does not
  enforce own/allied moat ownership.
- Search and movement surfaces are separate. Large search and physical restricted
  movement have different Goodsyard exceptions; the full restrictions in
  [MOVEMENT_SURFACE_PROFILES.md](MOVEMENT_SURFACE_PROFILES.md) remain relevant.

### Actual movement and special movement class

`0x1855A0` consumes packed nibbles, low nibble first, and passes the stored moat
word `+0x9C8` as the last argument of `0xDCE60`. Its other inputs include the real
unit ID, current native tile/row, next direction and movement class `+0x6EC`
(typed `+0x90`, currently named `N00000573` in the Extender).

For ordinary class 0, `0xDCE60` first accepts an outgoing direction bit at the
start **or** a reverse bit at the destination
(with separate fire-hesitation side effects). Otherwise its moat branch requires
the path marker; entering a completed-moat tile is then permitted, while leaving
it still observes blocked/wall/special-structure rules. The function has no
player/alliance argument and no generic digger-type whitelist.
This physical acceptance predicate is not identical to the outgoing-only edge
used by the ordinary native ground search.

Do not generalize that branch to every movement class. `0xDCE60` has separate
class-1 and other-class contracts. More importantly, **this caller `0x1855A0`
bypasses both `0xDCE60` and `0xDCD60` for class 1**. The Tunneler sets class 1 in
its tunnelling flow (`0x12E400`) after its special reconstruction. This is a
distinct subterranean state, not a normal type-level permission to change.

For normal movement, `0xDCD60` independently checks the physical surface for
Knight, Ladderman, Catapult, Trebuchet, Siege Tower, Battering Ram, Portable Shield,
Arab Horseman, Arab Ballista, Camel Lancer and Heavy Camel. A moat marker cannot
be used as a blanket bypass for walls, roofs, gates or these restrictions.
Rejection returns to native wait/replan/error paths rather than silently advancing.

### Military order admission and normal movement state

The ordinary player path is `8C5F0 -> Chore 17 -> 196100 -> 11B520 -> 196280`.
AI/patrol callers use different order flags. `196280` alone does not reproduce
the dispatcher's command authorization or set the military walking AI state.
`11B520` sets state 101 and formation destination fields for admitted units;
selected structure-exit failure paths use state 122 instead.

`11B520` validates target availability/flags/PCL before its member loops. The
normal region check passes the fifth argument from `117C70`, which observes a
live member's native connection mode `+0x9B8`; this is neither the type path
profile nor `DCE60`'s control mode. `117BC0` finds a live, not-killed member
standing on completed moat; `117820` supplies the all-Assassins predicate.
`E9D90/E9FF0` are later structure/exit fallbacks, not the main region decision.

Per-member life, kill, selection, inactivity and special-action conditions still
apply. Stationary types 40/41/61 are excluded. Mobile Catapult/Arab Ballista need
crew state 2, Siege Tower/Battering Ram 4 and Portable Shield 1. A positive group
return does not guarantee any admitted member or a successful unit path.
`118E00` is another dispatcher with its own state conditions and positive
`+0xA9E` requirement; do not copy the normal group predicate onto every caller.
Both ordinary command admission and true type/state movement ability are distinct
from permission to cross a friendly moat.

### Speed and terrain cadence

`19B260` handles completed-moat slowdown independently of a digger-type whitelist.
The terrain phase at manager-relative `+0x6C8` advances by 4 while below 24;
phase branches add 3, 4 or 6 to movement delay `+0x9A2`. Other terrain, height,
crowding and group-speed contributions remain active. `182B00` combines delay
with `+0x74C` and the type handler's speed bonus `+0x916` before calling `1855A0`.
Each tile takes eight fine steps; diagonal steps have no generic square-root-of-2
time multiplier. This static cadence does not establish the cost of every newly
eligible civilian job state. Pathfinding's existing AI-101-oriented cadence
helpers are not evidence of complete civilian work-state timing coverage.

### Sources, destinations, cargo and identity

- `BFD30` maps Good ID to store type through `0x2E76D0 + good * 4`.
  `B9280(manager,good,minimum,owner)` scans building IDs backwards, requires live
  state 2, matching store type/owner and stock, but has no PCL/distance filter.
  The caller's Access and Move determine subsequent reachability.
- `BF9F0` first prefers a matching non-full stocked pile, then an empty pile for
  store type 10. That branch does not itself call Access. Its food-store branch
  (type 19, food total below 250) does call Access before returning a candidate;
  workers can call Access again. These branches must not be conflated.
- `B9AA0` with an explicit building tests suitability/capacity; with ID 0 it
  searches weapon stores using Access and `C6EA0`. The latter checks live state,
  owner, type 11 and shared remaining capacity across all goods (capacity 50).
  `BBA40` also uses Access, quarry stock and distance/stock scoring.
- `BD490/BD470` recheck capacity on actual delivery. `C9080` only checks
  `abs(dx) < 3 && abs(dy) < 3` around an access coordinate, not connectivity.
  Delivery `B6100` uses the stored destination Global ID; a chosen store or
  successful path is not yet a goods receipt.
- Slot/global identities, crop states, prey reservation, cow pairing, carry and
  production-buffer updates remain separate from terrain permission. Some states
  retry, some try another target, some intentionally ignore a Move return, and
  some enter state 110/removal. There is no uniform native "failed Move resets
  the worker" contract.
- `198620` shortens an existing path and updates length/target; with an active
  intermediate connection it records a deferred shortening request. It is not a
  new PCL/resource selector. `19B9D0` is a work/pause transition, not a path builder.

### Home return and shared building access

`19B930` checks workplace ID at manager-relative unit `+0x990` against its saved
Global ID at `+0x9C0`. Building Global ID is manager-relative `+0x134`, stride
`0x32C`. Call `19B974` invokes `C90E0`; the caller-supplied R8 candidate ordinal
survives into that call although the generic decompiler signature omits it.
Success copies building access `+0x15A/+0x15C` to unit `+0x992/+0x994`; failure
returns 0. Neither branch publishes a path or sets the worker's AI state.

`C90E0(manager,buildingId,candidateOrdinal)` evaluates the **building owner's
Keep PCL to the building access**, not the requesting worker's current position.
It checks ID, access coordinates, height (within 16), surface mask `0x50501481`
and the flag-12/special-structure exception via `107160`. Connectivity passes for
Keep-PCL 0, equal PCL, a building-type bypass in `0x2E4FE0`, or positive
`E2610(owner,keepPcl,accessPcl,0)`. A valid existing access returns 1.

Otherwise `BACC0` prepares the candidate cursor and `BB3D0` searches alternate
access points. Its normal phases require connectivity and return 1; the final
fallback only requires a nonzero candidate PCL and returns **2**. These successes
write shared access coordinates. Full failure writes building access/status word
`+0x318 = 0` and returns 0; `C90E0` preserves the distinct 1/2 results.
This is shared mutable building state, also consumed by building/AI access logic.
A worker-specific Boolean is not a substitute for this contract.

## Additional native route publishers and unit-specific consequences

### Wander/random paths

`0x197050` is a separate publisher: it binds and clears the same unit-owned path
slot, clears the global moat/Assassin modes, calls `0xE4FC0` directly, and on
positive output writes path state/length/cursor/start fields and **zeroes `+0x9C8`**.
It does not call `0x196280` or `0xF4930`.

`0xE4FC0` requires an available coordinate and nonzero start PCL, seeds
`0xDAAC0` without a fixed destination, then chooses a random/wander path through
its distance/stamp data. Mode-dependent budgets are 80/200/500/1000/2000;
packed output is bounded by 2000 directions. Its random state, reversal and
tie-breaking are native simulation state. Covering normal requested movement
does not cover this path or make a worker's random route owner-safe.

### Mobile siege on completed moat

This is an independent terminal-state barrier, not merely a pathfinding profile.
In `0x182B00`, a staggered unit-update check tests Catapult (type 39) and Arab
Ballista (77). If the current tile flags match `0x50000000`, which includes bit
30 for completed moat, it writes AI state 110 and clears the path-plan word.
The guard is before the individual type handler.

The actual dispatch targets are `0x1520D0` and `0x171C50`. Their shared 109/110
state branch increments the timer word `+0x920`; above 32 it sets AliveState 3.
The later `0x182B00` state-3 path calls `0x1869C0`, which unregisters the unit,
updates player/group bookkeeping and clears its 0x490-byte record and 1000-byte
path slot. Thus an otherwise published moat path can lead to **removal** of the
mobile siege unit. This is confirmed static control flow, not a newly reproduced
gameplay incident. Crew validity and normal admission remain additional conditions.

Stationary Trebuchet, Mangonel and Ballista are separately excluded by ordinary
group-move admission. A terrain option is not evidence that they should acquire
a new movement command. Siege tents, null/debug and transient burning records
likewise cannot be treated as ordinary controllable soldiers by name alone.

| Camel / `158020` | No own route publisher in the handler. `197A10` turns toward a herd leader; it does not build a route. Existing movement can still be consumed. |

`BC540/BC5E0/BD320/BF300/BF510` select by building ownership/type/state, not by a
generic route test. Random building choice counts candidates and consumes native
random state; person selection can reserve a target. Their side effects must not
be mistaken for a pure Boolean access check.

Null and ARCHER_debug dispatch to `12A8E0`; Crow and Seagull to `158670/158680`.
Each of those entries is `C2 00 00` (`ret 0`) followed by padding. Siege tent
`158690` animates/ages toward its end state, with no route publisher.

Burning man `12B980` explicitly sets the unit control-player word to zero on
update; it initially uses a `197050` path and then dies/ends. Burning-animal
handlers `167BA0/167C70` are absent as independent functions in the selected
semantic index. Their direct PE disassembly has no call or movement publisher:
both clear player word `+0x6EE`, set `+0x8F8=1`, clear speed bonus, animate and
set AliveState 3 at the respective animation limits. These are terminal
owner-clearing transformations, not ordinary player-associated walkers.

### Moat work is not civilian work

`69D60` was initially described too generally during reconnaissance. Its actual
unit callers are **exactly the ten existing moat-digger handlers**:
`13F540,143400,145030,146A70,14AED0,169B70,174F90,178350,17B540,17CF50`.
The other two direct callers are `3E700/110740`. Unit order 6 maps to mode 1
(digging), order 7 to mode 2 (filling), followed by `6AF60` and movement/work state.
It is not the general resource/workplace selector for the 20 economic handlers.
The request unit ID is one-based, but its returned candidate index is **zero-based**
with `-1` for failure. Callers accept index 0. The selector's extra load/reservation
increment of 20 is applied only when the selected index is greater than 0; this
exact branch does not redefine the caller's success test. `3E700` supplies the
tribe leader and mode 1; `110740` supplies the actual unit/owner and mode 2, then
only copies its work-coordinate out values after successful `6AF60`.

Mode 1 includes ownership/diplomacy, record occupancy, moat flags and candidate
score checks. Different PCLs trigger the standing-on-moat `196840` probe and
`E7C40/E2610` reachability path (E2610 calls at `6A014/6A0C2`). Mode 2 has its
distinct fill/approach checks. This explains why true moat-work capability must
stay separate from the proposed ability merely to traverse a friendly moat.

### Worker pauses and herd waypoints are separate target families

Actual worker leisure uses `185430 -> BF0A0 -> 196280`, **not `69D60`**.
The pause state samples/increments its duration/attempt fields, then `BF0A0`
selects owned live priority buildings (well, maypole, garden, statue, shrine,
beehive, dancing bear), other staffed buildings as fallbacks and finally a saved
player fallback. It tries at most three random priority candidates. Reachability
is tested by an **actual route-producing `196280` call for this same worker**,
not by a pure `C90E0/E2610` query. Success already leaves the unit path published.
The caller later consumes it through `188340`; failure/duration completion
restores the saved work state and visit fields. A probe call would also consume
native randomness and mutate the unit route. See [WORKER_PAUSES.md](WORKER_PAUSES.md).

Herd waypoint generation adds an earlier spatial graph:
`117520 -> 124E80` (Deer), `125290` (Goat) or `125D00` (Rabbit), using `127E60`
and rabbit-specific `129010`. The manager at `3395E10` contains 80-by-80 sectors
of 10-by-10 tiles, stride `0xA0`. Start comes from the real tribe leader, divided
by 10 on each axis. Candidate sectors need a positive validity value and the
**same 32-bit sector-component value at +4** as the start; policy-dependent population/
danger fields add further restrictions. `129010` also requires positive `+0x50`.
Flood visits/distances and the resulting tribe waypoint array/count/index are
written before group and individual movement. Editor/special runtime mode
branches skip normal herd routing. An individual moat permission does not
automatically recompute this sector graph or create new cross-component waypoints.

## Persistent state, identity and saved paths

The path-mode word is part of native unit state, not only a transient mod decision.
The typed-view offset is `+0x36C`; the native wire/copy view that starts four bytes
earlier calls it `+0x370`. Their common manager-relative address is `+0x9C8`.

Native writers `86F80/13030` use descriptor table `336B20` through `52B0`.
The descriptor at `337030` has source VA `1867E8A58`, active flag 0, byte count
`0xB23900` (10000 * 0x490), compression enabled and tag 3015. Descriptor `337D80`
has source VA `187338278`, byte count `0x989680` (10000 * 1000), compression
enabled and tag 1171. Thus native unit mode and packed route bytes are saved.
The pre-save `186040` animal-count pass does not rewrite these route fields.

The modern load path `87D0` first calls `198180` to clear unit records/routes,
then matches descriptor tags and decompresses the current unit/path blocks
through its normal `CF20` path. No separate reset of the path-mode word was
found for these modern matching blocks. Historical format-conversion branches
are not a promise that every older format preserves this state identically.
Saved routes can therefore outlive the command that created them; neither a new
option nor a new route search proves that already stored paths were revalidated.
`15710` / Chore 56 also carries the 0x490-byte native unit record and 1000-byte
path slot. The stored marker lies in the checksummed unit region described in
[DESYNC_CAPTURE.md](DESYNC_CAPTURE.md), not its temporary excluded words. Matching
simulation policy across peers is required; this is not a multiplayer run.

Slot reuse, tanner/cow calls and follower/master calls also demonstrate why the
moving unit's identity must be established at each actual publisher. A current
type-update global, a representative group member or a previous command's mode
does not establish the owner of a later unit's output buffer.

## Existing Pathfinding integration snapshot [mod integration]

This section describes the inspected working tree, not Vanilla and not a proposed
patch. Source hashes and repository identities are recorded in the evidence JSON.

- `EnableFriendlyMoatTraversal` is a host-synchronized, default-false setting.
  `EngineOptions` freezes it per mission; `FriendlyMoatTraversalProvider.Enabled`
  also requires the shared pathfinding core. Command snapshots capture provider
  enablement, and the provider is process-rooted through `EngineHost`, mission
  subscriptions and simulation ticks. No early-plugin Update loop is required.
- `CanDigMoat` is currently used for **two different purposes**: true moat work
  capability and permission to use a friendly-moat route. It appears in command
  admission, cursor/group summaries, planning, attack approaches, placement,
  route qualification, live publication and tracking, as well as dig/fill target
  selection. The latter still explicitly requires real diggers. A global type-list
  expansion would conflate these contracts; there is no audit basis to grant
  civilians or other military types dig/fill work.
- `AnchorDigger`, `GetUnitMovePlan`, `TryFindFastRequiredRouteCore`, weighted
  publication and group/cursor dispatch all carry the present digger restriction.
  Rooting only one new boolean at the UI does not reach all these decisions.
- Existing route ownership uses the actual unit ID/global identity and
  `r_ControllableForPlayerId`. Moat ownership comes from `0x69560`'s tile-to-record
  mapping, record count/bounds, exact tile correspondence, and owner byte at
  moat record `+0x0C` (stride 0x10). Invalid records/owners are rejected. Own owner
  or equal diplomacy team is friendly. The native moat marker itself has none
  of these ownership checks.
- The owner-safe graph checks endpoints and diagonal corner moats, tile flags,
  heights, gate policy, current physical surface and route publication. Caches
  distinguish ground/friendly terrain, player, surface class and revisions;
  access fingerprints include alliances and portal/gate state. Native tile and
  direction changes invalidate topology. A full search per target candidate
  cannot be assumed cheap merely because the final movement uses shared fields.
- The current non-group path may deliberately keep Vanilla when an anchor answer
  is unavailable (`FastMoatRouting`, `fastAnchorSkips`). This existing behavior
  matters for automatic workers; changing the type filter alone is not evidence
  of continuous civilian path coverage.
- Published command hooks have process lifetime. Their Dispose path rejects
  disposal after publication; map/setting changes use logical state. The runtime
  project source-links `Shared.DependencyFreeJson`; no serializer change is part
  of this audit. No new runtime component, polling loop, packet or native hook
  has been installed here.
- The local Extender owns the type-surface (`0xDCD60`) and Assassin-selection
  (`0x196870`) detours. Its type profile/permission/override APIs act globally on
  a type, not on a unit/player/command. APIShared owns shared gate/search sites;
  Fixes also adjusts PCL rebuild and the `0xE7C40` component-visit storage when
  extended PCL arrays are enabled. These sources were inspected; this is not a
  live hook-overlap or multiplayer acceptance certificate.

## Audit boundaries and evidence interpretation

This document records static contracts, including all dispatch slots and the
identified requested/random movement, target-selection, access and terminal-state
families. It does not claim that all three requested options are already safe to
implement by one hook or one type-table change. No new hook ABI, displacement,
fallback or compatibility policy has been selected.

No game was started, no mouse/keyboard input was taken over, no save or installed
plugin was changed, and no mod/test code was built or modified for this audit.
Gameplay acceptance, route timing for newly admitted types, real host/client
determinism and behavior under ownership/diplomacy/terrain changes remain separate
future verification tasks. Unknown dynamic cases must not be silently classified
as accepted by this static audit.
