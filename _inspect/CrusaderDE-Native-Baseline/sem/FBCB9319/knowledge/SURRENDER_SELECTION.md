# Surrender selection and multiplayer checksum audit

Native build SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2`. The installed Script Extender inspected for the managed path was `2.10.1.0` (local fork commit `a8ba202f6ec7966bd115b59a6088a0077ce727a0`). Addresses below are RVAs for this build; none is used as a runtime call target by the Surrender fix.

`DLL_RunTick` (`0x86680`) reaches the simulation path `0xCDE60` and checksum scheduler `0xD1AD0`. Every 200 map ticks, the checksum builder `0x22020` computes fourteen category aggregates. Its first bucket scans unit IDs 1..9999. For each unit, `0x78E0` hashes 0x404 bytes beginning at the unit's `r_AliveState` offset 0x88, plus the separate 1000-byte packed path plan and three scalar values. The builder temporarily masks eight bytes at unit offset 0x418. The unit's `r_UnitSelected` at offset 0xAE is inside the hashed interval and is not masked. The unit record is 0x490 bytes; native manager and per-unit address arithmetic agree with the installed Script Extender layout and one-based game IDs.

`0x27960` compares the fourteen category aggregates and sends mismatch opcode 0x65 (101). On a flagged first bucket, `0x26D30` compares per-unit checksums, stores the first offending unit ID and sends detail opcode 0x38 (56). `0x27C50` can queue resync opcode 0x36 (54) when the aggregate mismatch is established. These functions have candidate symbolic names in the export; the relevant branch and data flow were checked directly in the current decompilation. The observed opcode 101 flags and opcode 56 unit IDs corroborate the assignment, but other categories and all possible resync triggers were not exhaustively attributed.

Two Surrender traces showed exactly four different bytes in the full Lord unit record at the checksum tick: offsets 0x10, 0x12, 0x13 and 0xAE. Only 0xAE lies in the hashed record interval. After player 2 surrendered, Lord unit 13/global 1356740 had `r_UnitSelected=0` on the host and `2` on the client at map tick 600; Vanilla's detail opcode identified unit 13. After player 1 surrendered, Lord unit 11/global 1356738 had `r_UnitSelected=1` on the host and `0` on the client at tick 1000; Vanilla identified unit 11. Packed path-plan and the three extra per-unit scalar inputs were not captured in those traces, so the selection field is a strong sufficient explanation, not a proof that no other checksum input differed.

Native `0x19A5D0` handles individual and all-unit deselection. In its individual branch it clears `r_UnitSelected` and decrements `GameUnitManager.r_SelectedChimpsCount[playerId]` when the unit was selected. The first count element is at manager offset 0x24 in the installed assembly (`Marshal.OffsetOf`), consistent with the native expression `manager[(playerId + 9)]`; the Extender source comment saying 0x28 is one word late. The final unit deletion `0x1869C0` calls this handler and then zeroes the unit record and path plan. The installed Extender's `KillUnit` instead sets health to 1 and calls melee damage with maximum damage; the dead Lord can remain in its slot through the next checksum. `GamePlayerManagerAPI.SetSelectedChimps(empty)` queues a two-phase local input gesture and is not a synchronous replacement for the selection-field correction inside the common Surrender Chore.

Implementation rule: after the existing synchronized Lord kill, revalidate unit slot/global identity, clear an observed selection flag for the surrendering player and decrement a positive selection count once. Treat zero counts and unexpected selectors as anomalies, never underflow or guess another player's count. A local queued HUD deselection may follow, but checksum correctness must already hold before that deferred gesture. Test selected and unselected Lords, both surrendering peers, a normal enemy kill, repeated Surrenders, and the next 200-tick checksum boundary.
