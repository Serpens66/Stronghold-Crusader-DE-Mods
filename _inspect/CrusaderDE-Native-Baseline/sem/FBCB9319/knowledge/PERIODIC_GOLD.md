# Incoming gold and periodic ExtraFeatures amounts [Scope: Vanilla + mod integration]

Native SHA-256: `FBCB93195FC7EFCA9BDAC5204852EFDD76F9818F59A6711750D77C9CEF2831E2` (installed canonical DLL rechecked on 2026-10-25). This is a static machine-code finding; in-game and multiplayer acceptance remain separate.

## Producer, storage and consumer

The installed Extender exposes `GamePlayerManagerAPI.AddIncomingGood(int playerId, eGoods good, int amount)`. It validates the one-based player ID and performs a signed Int32 addition into the incoming table, through an `int*` view of `r_incomingNull`. `eGoods.STORED_GOLD` indexes `GamePlayerResources.r_incomingGold` at record offset `0x4A8`; its source declaration is UInt32, but the consumer comparison is signed. The player record stride is `0x583C`, with the first record at player manager + `0x1343FC`. Thus the player-indexed native incoming-gold address is image + `0x379B278 + playerId*0x583C`; the signed current-gold balance is image + `0x379B2DC + playerId*0x583C` (record offset `0x50C`). These addresses are evidence only, not new runtime accesses.

Three incoming-gold consumer code paths begin at RVAs `0xA4FE0`, `0xA50E0`, `0xA5200`; their dispatch-table references are `0x2DEC20`, `0x2DEC28`, `0x2DEC30`. They derive the one-based owner from the current building and skip gold processing under the existing global update/mode guards (including native mode 1 and 6). At `0xA506B`, `0xA5183`, `0xA52A3` they read incoming gold, execute TEST/JLE, and skip any zero or negative pending amount. Positive values transfer 100 when >1000, 10 when >100, otherwise 1. The same amount is subtracted from pending and added to current gold. The following writes update the two displayed gold words and the presentation-dirty flag. This is gradual delivery tied to eligible building updates, not an immediate credit or a fixed additional 400-tick settlement.

The installed Extender's `SubtractIncomingGood` clamps the pending value at zero; it cannot debit already credited gold. `SetPlayerGold` writes only the current signed gold balance; pending incoming gold remains untouched. For a real periodic debit, ExtraFeatures therefore computes max(0, balance + signed amount) with Int64 intermediate arithmetic and uses that public setter. Positive periodic amounts use the public incoming-good API, bounded by Int32.MaxValue minus nonnegative balance and pending credit. This prevents this feature from creating signed overflow without changing foreign accounting.

## Evidence and limits

All three complete leaf-code bodies were decoded directly from the hash-checked installed binary, including entry/owner setup, all guards, transfer thresholds, pending/balance writes, display writes and returns. Audit instructions and byte hashes are retained in workspace `.work/a/periodic-gold/001/native-audit.json`. The generic semantic function inventory lacks these three leaf entries; their DATA references and machine instructions establish their identity. Do not infer zero/negative support from the UInt32 field name or from successful AddIncomingGood invocation. Gold input must never be negated in Int32 (Int32.MinValue is accepted by the mod setting).

## Original scheduling and corrected integration (2026-11-01) [mod integration]

The original implementation used the Extender OnTick argument and `Director.instance.getSimTickCount()` at mission completion. These are the same local engine-run counter, not the saved native map counter. The real installed Director increments it before deciding `FrameToSkipMP` and low-FPS compensation and before `EngineInterface.run(flag)`. It resets in `startSimThread`; it does not preserve the save's interval phase. Two peers can therefore book the same configured amount in different native ticks. Identical fake OnTick sequences in the original offline test did not cover this defect.

The existing hash-bound native path is `DLL_RunTick` RVA `0x86680` -> game update `0xCDE60` -> time update `0xD1AD0`, with the SE context callback at `0xD1D4F`. The game update increments the native Int32 counter at RVA `0x3665F58` immediately before calling the time update, only through its advancing-simulation branch (including the `mpFrameSkip == 0` guard). Thus the existing callback context is appropriate; its managed payload is not an interchangeable clock. These data-flow findings are confirmed by the decoded native code and installed managed IL; generic inventory function names remain candidate names.

APIShared's additive `Simulation.SimulationTickEvents` uses that existing SE event as its publisher but ignores the local argument and reads the public `GetElapsedMapTicks()` once per publication. It gates on the central lifecycle's ready Current mission, distinguishes sessions, suppresses duplicate/older ticks, and isolates its own consumers. It installs no native or managed patch and leaves SE frame counts, timestamps and timers unchanged. The Extender getter loads UInt64 and returns the low Int32 of its resolved CurrentGameTickVA; the source validates the full public resolved read range within the loaded image before activation. Gold startup/reactivation use the same native source. The signed accounting above is unchanged.

The adapter still depends on the upstream Extender reaching its event; earlier trigger/runner/subscriber exceptions can suppress delivery. The service cannot repair that independently.
